#28 Agent-to-agent (A2A) through the gateway

Detail: guide #28. Lab: privilege-a2a-anthropic-demo-LAB (the two agents). This is the order that worked.

Needed from other systems

SystemWhat you need from it
AnthropicA real API key. Privilege holds it server-side as the provider's Real Key; the agents only ever hold Privilege virtual keys. Allowed model IDs must be exact (we used claude-sonnet-4-5 and claude-haiku-4-5-20251001).
KubernetesA namespace the gateway mesh can reach. Apply the lab's k8s/deployment.yaml: it starts the worker agent (A2A on /a2a) and the MCP server (/mcp). A process on 127.0.0.1 cannot be reached by a hosted gateway. Ours: namespace ping-devops-cmuir.
Presenter's machineDocker (OrbStack) and the lab's .env. UI at https://local.ping-devops.com:8443/privilege-a2a/.

In Privilege

  1. Provider: add the Anthropic provider with the real key; allow the two models.
  2. Register two apps (Agentic Apps → Add Application), on the gateway's mesh cluster:
    WorkerMCP
    TypeRemote AgentMCP
    Backendhttp://workeragentdemo.<ns>.svc.cluster.localhttp://mcpdemo.<ns>.svc.cluster.local
    Path/a2a/mcp
    Auth ModeNone (never Pass Agent Token)None
    Our tenant's worker app is named workeragentdemo2; use whatever name you register and put it in the URLs below.
  3. Worker agent (Agent Registry → Add Agent): scopes llm + mcp, one allowed model, MCP Server = the MCP app, then Configure Tools and allow each tool. If the tool list is empty, re-save the MCP app so discovery re-runs with the backend up.
  4. Main agent: scopes llm + a2a, a different allowed model, Remote Agents = the worker app. Selecting the app is the grant. Give it a different custodian from the worker: remote-agent grants follow the custodian, so one shared custodian lets the agents reach each other's agents.
  5. Unauthorized agent for the refusal test: scope a2a, no Remote Agent selected, a third custodian. (On our tenant the worker's own key, which has no a2a scope, was used and was refused the same way.)
  6. Turn on Discover A2A agent card on the worker app once it is running.

Wire the lab to the gateway

MAIN_AGENT_KEY=<main agent key, pasted once>
ANTHROPIC_BASE_URL=https://<gateway>/llm/anthropic
MAIN_AGENT_MODEL=<model id allowed on the main key>
WORKER_AGENT_MODEL=<model id allowed on the worker key>
WORKER_A2A_URL=https://<gateway>/<worker app>/a2a
WORKER_TRACE_URL=https://<gateway>/<worker app>/trace
  • The worker key goes in the cluster Secret privilege-a2a-demo (with the main key), not in .env.
  • A doubled paste is refused as invalid virtual key.
  • docker-compose.yml must read WORKER_A2A_URL and WORKER_TRACE_URL from .env (fixed in lab commit 9552e53); an older compose pins them to the local worker and ignores .env.

#29 Human-in-the-loop approval

Detail: guide #29. This is the one that needs a person with a phone.

Needed from other systems

SystemWhat you need from it
PingID (approver's phone)The PingID app paired to the approver's account (Authentication → My Account → manage MFA devices). The approver confirms by push ("Are you trying to sign on?", blue button) or the 6-digit passcode. Without a paired phone the approval cannot be confirmed.
An MCP server behind the gatewayAny registered MCP app with at least one tool. The reference used opensearch and the tool IndexMappingTool.
An MCP clientAnything that can call a tool through the gateway with an Authorization: Bearer key and show the full response (a 403 body, not just "failed").

In Privilege

  1. Tenant MFA on: user menu → Settings → Tenant Profile → Tenant Information → Edit → MFA = Enabled. Save.
  2. AI Policy (AI Policies → create), authoring tab Build a rule:
    FieldValue
    Name / Stateopensearch-hitl (cannot change later) / Active
    WhenMCP tool call, on the request
    OutcomeRequire human approval
    MCP server / Toolthe app's name / one named tool or any tool
    Grant shape / approvalsThis transaction only / 1
    Agent retry window90 s
    Request stays open120 s
    Who may approveAnyone with admin rights (or a named group or user)
    Reason shown to callerfree text
    The detail page should read Active, Validation Valid, "1 refusal, asks a human".
Four things that stopped us on 2026-11-19: (1) tenant MFA was off, so nothing could prompt PingID; (2) a hold sends no notification, the PingID prompt appears only when the approver clicks Approve; (3) the approver must be the account signed in to the console, and the policy should name that account (one earlier request was approved by another account, with no PingID); (4) a policy created through the API needs State: Active or the gateway only shadows it. Also, an agent key gets a bare 403 on a door set to user-token authentication. Details in guide #29.

#30 SPIFFE identity (Federated Identity)

Detail, results and log lines: guide #30. The gateway trusts a short-lived JWT-SVID instead of a static key, and checks issuer, subject (the SPIFFE ID) and audience.

Needed from other systems: the SPIFFE issuer

Privilege only verifies tokens. Something else must mint JWT-SVIDs and publish a public JWKS the gateway can fetch over HTTPS (no auth, not behind a login redirect). Our real run used SPIRE 1.7.2 in the SE Kubernetes cluster:

PieceOur value / requirement
SPIRE serverStatefulSet spire-server, image spire-server:1.7.2 (1.12.4 crashed on the volume; do not bump without re-testing). Trust domain se-cluster.ping-devops, jwt_issuer = "https://spire.ai-demo.ping-devops.com" (this string is the token's iss), default SVID TTL 1 h.
OIDC discovery providerSidecar oidc-discovery-provider:1.7.2 in the server pod, plain HTTP on 8090 (TLS ends at the ingress).
Public JWKShttps://ai-demo.ping-devops.com/spire/keys through its own auth-free ingress (spire-oidc). Do not add it to an ingress that carries auth-signin annotations: unauthenticated fetches get a 302 to login and the gateway cannot read the keys.
AgentPod spire-agent-1, attested by join_token (PSAT was blocked by cluster RBAC). Non-default socket: always pass -socketPath /run/spire/agent-sockets/socket.
Workload entriesValid: spiffe://se-cluster.ping-devops/ns/ping-devops-cmuir/sa/mcp-agent. For the mismatch test, a second entry for .../sa/other-agent.

Full SPIRE ops notes (join tokens, bundle, gotchas): ~/Development/HANDOFF-2026-11-19-spire-se-k8.md. For a rehearsal with no cluster, the standalone spiffe-issuer-LAB mints the same three tokens locally.

Leave the key's own workload identity empty (it is mutually exclusive with an identity custodian), and clear any user reference if you cloned a human-custodied key. An identity with no key behind it logs rebuilding 0 key(s) and accepts nothing.

Alternative issuer: a PingFederate token

The same Federated Identity object trusts any OIDC issuer, so a PingFederate-minted JWT works without SPIFFE. Verified live 2026-11-13 on this gateway (guide: AI-DEMO2 privilege/GATEWAY-WORKLOAD-IDENTITY-SETUP.md; lab: workload-identity-LAB, real mode). It proves the federated-identity mechanism, but it is not SPIFFE-shaped, so keep it as the "and it also works with your IdP" follow-up, not the #30 answer.

WhereWhat to build
PingFederate
  1. An OAuth client with grant client_credentials.
  2. A JWT access token manager (unique Key ID) with audience and resource URI = the gateway app URL (https://<gateway>/<app>/mcp). Do not add scope to the attribute contract.
  3. Access token mapping for the CLIENT_CREDENTIALS context: sub and client_id from the ClientId, and act = #{"sub": "<agent id>"} as an object, not text.
  4. Set the client's default token manager to that one. Every token request must send resource=<app URL>, or a different manager answers (wrong aud, no act) and the gateway returns 401 token_not_found.
  5. Decode a token: you need iss, sub, aud, client_id, act.sub, scope.
Privilege appMCP app whose URL ends in exactly /mcp, Auth Mode Pass Agent Token. Needs gateway privilege-aigw v1.261024 or later.
Privilege identityFederated Identity with type OIDC Provider, issuer = the PF base URL, key source = fetch from <pf>/pf/JWKS, subject *, audience = the app URL, required claims act.sub and client_id, scope mcp.
Privilege keyAgent key with the identity as custodian and the app selected. Edit the key's own grant; a separately created API policy is deleted by the gateway within seconds.
Callcurl https://<pf>/as/token.oauth2 -u "<client>:$PF_CLIENT_SECRET" -d grant_type=client_credentials -d "scope=..." -d "resource=<app URL>", then use the token as the bearer on tools/list. Keep the client secret in an environment variable, never in a file you commit.

If something fails

You seeLikely cause
401 invalid virtual key (#28)Key typo, doubled paste, revoked or expired.
Bare 403 on the allowed agent (#28)Remote Agent not selected on that agent, the key lacks the a2a scope, or the app is on Pass Agent Token. Read the gateway log.
Empty tool list (#28, #30)Re-save the MCP app so discovery re-runs with the backend up.
Protected tool call just succeeds (#29)Policy not Active or not matching the app and tool name; or not yet propagated (4 min).
Approval never completes (#29)PingID not paired to the approver's account, or tenant MFA still off.
Valid SVID gets 401, no workload token log line (#30)No agent key behind the identity, identity disabled, or not yet propagated.
Valid SVID rejected on audience (#30)The token's aud is not exactly the audience the identity displays.
JWKS cannot be fetched (#30)The JWKS URL sits behind a login redirect or is not public HTTPS.
