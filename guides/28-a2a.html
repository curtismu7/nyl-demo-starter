#28 Agent-to-agent (A2A) calls: set up on PingOne Privilege

Two authorized test agents talk through the gateway's A2A path, and an unauthorized agent is refused. · back to the demo starter

What this proves

The test: configure two authorized test agents to communicate through the supported A2A path. In Privilege that path is the gateway's Remote Agent route (/<app>/a2a). Each agent holds its own Agent Access key; the gateway checks the key, the a2a scope and the grant on every hop.

main agent  --(1) A2A message/send, main key-->  gateway --> worker agent
main agent  --(2) model call, main key--------->  gateway --> model provider
worker      --(3) model call, worker key------->  gateway --> model provider
worker      --(4) MCP tools/call, worker key--->  gateway --> MCP server

It must be a real run. The mock A2A Lab on the starter page rehearses the story; it does not exercise Privilege. This guide is the real setup. Use the demo lab privilege-a2a-anthropic-demo-LAB as the two agents.

Before you start

NeedDetail
Privilege console adminCan create Agentic Apps and Agent Registry entries.
Two custodiansTwo different people (or accounts) to be custodians of the two agents. Remote-agent grants follow the custodian, so one custodian for both agents lets them reach each other's agents.
A model provider keyCreating an llm-scoped agent requires the real upstream provider key; Privilege holds it server-side and the agent only keeps the virtual key.
A place the gateway can reachThe worker agent and MCP server must be reachable from the gateway's mesh cluster. A process on 127.0.0.1 cannot be reached by a hosted gateway. The lab ships k8s/deployment.yaml for this.

Deploy the worker agent and MCP server

From the lab repo, apply k8s/deployment.yaml to the namespace the gateway mesh can reach. This starts two services: workeragentdemo (the worker agent, A2A on /a2a) and mcpdemo (the MCP server, /mcp). Registering the apps before they run is allowed; discovery in step 3 needs the MCP backend up.

Register the two apps

Console: Agentic Apps → Add Application, on the mesh cluster of the gateway that serves traffic.

Fieldworkeragentdemomcpdemo
TypeRemote AgentMCP
Backendhttp://workeragentdemo.<namespace>.svc.cluster.localhttp://mcpdemo.<namespace>.svc.cluster.local

Auth ModeNone (never Pass Agent Token: it refuses key callers)None

Create the worker's agent

Console: Agent Privilege → Agent Registry → Add Agent. The name cannot be changed later.

  • Identity & Access: a name, the first custodian, an expiry, scopes llm + mcp.
  • Gateway & Apps: one provider, one allowed model, MCP Servers → mcpdemo, then Configure Tools and allow each tool. If the tool list is empty, save the mcpdemo app again to re-run discovery now that its backend is up.
  • Runtime Protection: leave the defaults, or set the AI Guard thresholds you want to demonstrate.
  • Review & Create: copy the key now and treat it as a secret.

Create the main agent

Same wizard, with a different custodian: scopes llm + a2a, a different allowed model, Remote Agents → workeragentdemo. Selecting the app is the grant; saving auto-creates the policy for the custodian.

The grant on our tenant: policy MainAgentA2aMcpTools has an A2A rule to the worker app (API view). The console's key page does not list it, although the gateway honours it; selecting the Remote Agent on the key in the wizard is the documented route.

Create a third agent with no grant (the unauthorized one)

Create one more agent with scope a2a and no Remote Agent selected. It is the "unauthorized agent" for the refusal test. Use a different custodian again.

Turn on agent-card discovery

On the workeragentdemo app, switch on Discover A2A agent card once the worker is running.

Store the keys and point the lab at the gateway

Paste each key once (a doubled key is refused as invalid virtual key). The main key goes in the lab's .env; the worker key goes in the cluster Secret the worker reads.

MAIN_AGENT_KEY=<main agent key>
WORKER_AGENT_KEY=<worker agent key, cluster Secret>
ANTHROPIC_BASE_URL=https://<gateway-host>/llm/anthropic
MAIN_AGENT_MODEL=<model id allowed on the main key>
WORKER_AGENT_MODEL=<model id allowed on the worker key>
WORKER_A2A_URL=https://<gateway-host>/workeragentdemo/a2a
WORKER_TRACE_URL=https://<gateway-host>/workeragentdemo/trace
WORKER_PUBLIC_URL=https://<gateway-host>/workeragentdemo/a2a/jsonrpc

Restart the lab. The main agent's startup log should now say it uses the gateway, not direct Anthropic.

Changes to apps and policies take about 4 minutes to reach the gateway. Do not conclude a failure sooner.

Run the test

  1. Authorized: ask "Review Carol Nguyen's access". The main agent delegates to the worker over A2A and the worker reads data through MCP. Expect an answer.
  2. Unauthorized: send the same A2A message/send with the third agent's key: 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST "https://<gateway-host>/workeragentdemo/a2a/jsonrpc" \
  -H "Authorization: Bearer $THIRD_AGENT_KEY" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"message/send","params":{"message":{"role":"user","messageId":"m1","parts":[{"kind":"text","text":"Hello"}]}}}'
    Expect 403. Repeat with the main key: expect 200.

Evidence that it was real

  • The status codes: the allowed A2A call returns 200, and the key without the a2a scope returns 403 (key not scoped for a2a access). On our deployment the gateway log does not record these calls per call, so the codes are the evidence.
  • The console's agent activity / audit view shows both agents by name.
  • The lab's startup log shows the gateway URL, not direct Anthropic.
